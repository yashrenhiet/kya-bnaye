## 0. Roles and standards (applies to every task in this repo)

This is not a toy project. Every contribution — human or agent — is held to these three
hats, worn in this order depending on the task:

### As a Principal iOS/Swift Developer (writing code)
- Code ships at **production quality**, not hackathon quality, even for v1. No shortcuts
  that we'd be embarrassed to explain in a code review.
- **Swift 6 language mode, strict concurrency, zero warnings.** Warnings are errors
  (`-warnings-as-errors`) in the gate and in CI. No `@unchecked Sendable` or
  `nonisolated(unsafe)` unless an ADR justifies it.
- **Value types by default.** Domain models are immutable `struct`s and `enum`s that are
  `Sendable`, `Equatable` and `Hashable`. No mutable God objects and no class hierarchies
  in `KyaCore`.
- **No force unwraps (`!`), `try!` or `as!`** in production code. Unwrap with
  `guard let`, and model failure with typed `throws` or `Result`. Tests may use
  `try #require(...)`.
- **Views stay small and dumb.** Business logic lives in `KyaCore` or an `@Observable`
  store, never inline in a `body`. If a `body` needs a comment to explain what it's doing,
  extract it instead. Keep observation narrow, so one badge change doesn't re-render the
  whole screen.
- **Accessibility through SwiftUI modifiers:** `accessibilityLabel`, `accessibilityValue`,
  `accessibilityAction` (a non-gesture path for every swipe), and `accessibilityHint`
  where it isn't obvious. Support **Dynamic Type** (semantic text styles, no fixed font
  sizes) and respect `accessibilityReduceMotion`.
- **Every public API in `KyaCore` is documented** (`///` doc comments) with pre- and
  postconditions where they're not obvious. No unresolved TODOs merged into `main`:
  either do it, ticket it in the plan, or don't write the comment.
- **Errors are handled, not swallowed.** No empty `catch {}` and no `try?` that discards
  a meaningful failure. Async failures surface a user-facing state (loading, empty or
  error), never a silent no-op or a crash.
- Every feature ships with the tests described in §6 **before** it's considered done.
  Tests come first for `KyaCore` and at least alongside the code for the app.

### As a Senior Code Reviewer (reviewing any diff, including your own)
Before calling anything done, review it as if someone else wrote it and your name is on
the approval:
- **SOLID and DRY, pragmatically.** Flag duplicated logic, leaky abstractions, and classes
  doing two jobs — but don't invent interfaces or layers nobody asked for (YAGNI still wins).
- **Negative-path audit on every change:** empty pantry, zero recipes, corrupted backup
  JSON, mid-swipe app kill, clock/timezone edge cases (expiry, "days since cooked"),
  duplicate ingredient aliases, offline/first-run state.
- **No dead code, no commented-out blocks, no placeholder strings** left behind.
- **Diffs stay small and reviewable** (target < 300 lines per PR, per §7) with a clear
  single purpose — reviewability is a feature, not friction.
- Accessibility and performance are review blockers, not follow-up tickets (see §4, §6).

### As a Senior Software Architect (planning structure and technical decisions)
- Every non-trivial decision gets **at least two options weighed** (even briefly) before
  landing on one, with the trade-off written down — see the ADR list in §5.8. "Because it's
  familiar" is not a reason on its own.
- **Protect the dependency rule in §5.3.** It is the most important architectural
  invariant in this codebase. `KyaCore` must never import SwiftUI, SwiftData or UIKit,
  and views must never import SwiftData. Any PR that breaks this is rejected, however
  small it looks.
- **Zero third-party dependencies as a policy.** Adding any package needs an ADR,
  because the corporate proxy may block it (ADR 009).
- **Design for the extension points we already know are coming** (cloud sync in v2, a
  second recommender mode, more languages) without building them now. New adapters and
  new `RankingStrategy` implementations should plug in without touching the core.
- Think about **failure modes and data integrity** before features: what happens to the
  pantry if a SwiftData migration fails, what happens to `SwipeEvent` history if the
  device runs out of storage, and what the recovery path is.

### As an Experienced UX / Product Designer (screens, layout, colour, interaction)
- Every screen decision gets discussed **before** it's built, the way a designer would
  present it: what's the user's emotional state right now (hungry, tired after work,
  indecisive), what's the one primary action on this screen, what happens if they do
  nothing.
- **Visual language should feel like a warm Indian kitchen, not a generic productivity
  app**: think turmeric/masala-inspired warm tones, appetising food photography as the hero
  of every card, generous whitespace so a hungry, tired user isn't asked to parse a dense
  UI. Avoid sterile corporate blues and cold greys as primary colours — warmth over
  clinical.
- **Typography and hierarchy:** one clear headline per screen and legible body text
  (the `.body` text style at the default size, scaling with Dynamic Type). Dish names and
  photos are always the most visually dominant element on a card, never crowded by chrome
  (badges, buttons, meta text).
- **Design tokens over hardcoded values.** Colours, spacing (4/8/12/16/24 scale), radii
  and type styles live in `KyaBnaye/KyaBnaye/Theme/` and are reused, never re-typed per
  screen.
- **Every interaction needs a visible affordance and a non-gesture fallback** (already a
  rule for swipe in §4) — a UX review is not complete until it's checked against WCAG 2.2 AA.
- Colour and layout proposals are **presented with rationale and at least one alternative**,
  the same way a design review would, before being locked into the theme tokens.

## 1. What this is

**kya-bnaye** ("what should I make") is a native **iOS app** (Swift/SwiftUI) that answers
the daily Indian-household question "what do I cook?" using two swipeable modes:

- **Kitchen mode** (default): dishes you can cook **with what's at home right now**.
- **Craving mode**: dishes you'll **love**, based on a taste profile learned from your
  swipes — whether or not the ingredients are at home.

Both modes share one Tinder-style swipe deck: **swipe right = "want this"**, **swipe left =
"not today"**. Every swipe teaches the app your taste. Right-swiped dishes become
**Today's picks**; missing ingredients become a shopping list.

### Design principles (every feature is judged against these)
1. **Answer "kya bnaye?" in one swipe session.** The deck is the product.
2. **Logging must be near-zero effort.** Stock is `Plenty / Low / Out`, never grams. Staples
   (salt, oil, haldi…) are assumed present unless marked Out. If a feature needs typing,
   question the feature.
3. **Offline-first.** No login, no network required for core value. Data stays on the phone.
4. **Suggest, never assume.** Anything inferred (used-up items, expiry) is pre-filled for a
   one-tap confirm, never applied silently.
5. **Explain every recommendation.** e.g. "Uses your palak (expires tomorrow). Nothing missing."
6. **Indian kitchen by default.** Sabzi/kirana/dairy categories, rice-vs-roti rotation, pan-Indian recipes.

- **Home** = the swipe deck. Mode toggle at top. Right swipe → pick sheet (View recipe /

text and icon rather than colour alone, full VoiceOver labels and actions, reduce-motion
respected (cards fade instead of fling), and Dynamic Type up to the accessibility sizes.

## 5. Architecture

### 5.1 Tech stack

| Concern | Choice | Why |
|---|---|---|
| Language | **Swift 6.4**, Swift 6 language mode, strict concurrency | Data-race safety at compile time |
| UI | **SwiftUI**, iOS 17+ | First-party, declarative, no downloads |
| State | **`@Observable` stores** (Observation framework) | Fine-grained updates, plain Swift, testable without views |
| Local DB | **SwiftData**, behind `KyaCore` repository protocols | First-party, migrations, in-memory store for tests |
| Navigation | **`NavigationStack` + `TabView`** | Value-based paths, deep-link ready later |
| Tests | **Swift Testing** (`@Test`, `#expect`), XCUITest for E2E | First-party, parameterised tests |
| Format/lint | **`swift format`** (bundled with the toolchain) | No download; `lint --strict` in the gate |
| CI | GitHub Actions, macOS runner: `swift build`/`swift test` for `KyaCore`, `xcodebuild` for the app | Only `actions/checkout` as a third-party action |
| Dependencies | **None (policy)** | The proxy may block packages. Adding one needs an ADR |

`KyaCore`: `swift-tools-version:6.0`, platforms iOS 17 and macOS 14 (so `swift test`
runs on the host).

`KyaCore` is isolated on purpose: the recommender has to be independent of the UI and
heavily tested. A separate data package would be ceremony at this size. The adapters
live in `KyaBnaye/KyaBnaye/Data/` until a second consumer, such as a widget extension,
justifies splitting them out.

### 5.3 Dependency rule (ports and adapters)
```
Features (views + @Observable stores) ──► KyaCore (domain + use cases + ports)
                                                ▲
KyaBnaye/Data (SwiftData adapters) ────────────┘  implements ports
```
- `KyaCore` imports **Foundation only**. It never imports SwiftUI, SwiftData or UIKit,
  and it has no package dependencies.
- SwiftData `@Model` classes exist **only** in `KyaBnaye/Data/`. They map to and from
  `KyaCore` structs at the adapter boundary, and no `@Model` type crosses a port.
- Views observe `@Observable` stores, which call `KyaCore` repository protocols. **No
  view imports SwiftData, and no view uses `@Query`.** ADR 009 records why this beats the
  idiomatic `@Query` style.
- Swapping SQLite for cloud sync in v2 = a new adapter, zero domain changes.

### 5.4 Domain model

All types are immutable `Sendable` structs. Enums are `String`-backed, and each raw value
matches the seed/backup JSON name **byte for byte** (camelCase, e.g. `case indoChinese`
→ `"indoChinese"`, `case oilGhee` → `"oilGhee"`, `case neverShow` → `"neverShow"`).

```swift
struct Ingredient   { id, name, aliases: [String], category, role, buyFrom, shelfLifeDays: Int?, isUserCreated }
  enum Role:     core | flavor | optional | staple   // drives scoring weight; "staple" is a role, not a flag
  enum Category: sabzi | fruit | dairy | grains | dal | masala | oilGhee | packaged | other
  enum BuyFrom:  sabziwala | kirana | dairy | other

struct PantryItem   { ingredientId (key), level, expiresOn: Date?, expiryIsEstimated, updatedAt }
  enum StockLevel: plenty | low | out

struct Recipe       { id, name, mealTypes: Set<MealType>, minutes, base,
                      ingredients: [RecipeIngredient], steps: [String], tags: DishTags,
                      imageAsset: String?, isFavorite, isHidden, source }
struct DishTags     { region, dishType, flavours: Set<Flavour>, heaviness, protein }   // closed enums
  enum Region:    north | south | east | west | gujarati | punjabi | indoChinese | continental | street
  enum DishType:  dal | curry | drySabzi | rice | bread | breakfast | snack | sweet | onePot
  enum Flavour:   spicy | tangy | sweet | savoury | mild      // non-empty set
  enum Heaviness: light | medium | heavy
  enum Protein:   paneer | dalLegume | egg | chicken | mutton | fish | vegOnly
  enum Base:      rice | roti | bread | none                  // rotation penalty
  enum Source:    seed | user
struct RecipeIngredient { ingredientId, quantityText ("2 katori"), isOptional }

struct MealLog      { id, recipeId, mealType, cookedAt }
struct SwipeEvent   { id, recipeId, action (right|left|neverShow|undo), mode (kitchen|craving),
                      at, deckSeed, undoesEventId: String? }
                    // append-only; TasteProfile and TodaysPicks are derived from it, never stored
struct ShoppingItem { id, ingredientId: String?, customName: String?, reason (out|low|recipe|manual),
                      recipeId: String?, isChecked, createdAt }
```

Rules: one `PantryItem` per ingredient (key = ingredientId) · matching is **exact on
canonical id after alias resolution, never substring** (avoids the "rice" matches "rice
flour" bug seen in prior art) · unknown user input becomes a `source=user` Ingredient
instead of failing.

### 5.5 Recommender — two modes, one engine

Full design: **`docs/design/RECOMMENDER.md`**. Summary:
- `RankingStrategy` protocol, Strategy pattern: **KitchenRanker** (pantry coverage,
  core/masala/staple role weights + rarity bonus, expiry boost, tiers) and **CravingRanker**
  (learned taste affinity, pantry as a small hint only).
- Shared penalties: repeat cooldown (7/14/28/56-day steps + 90-day "rut"), left-swipe
  cooldown (hidden 3 days, down-ranked 14 days), same-base-as-last-meal (rice after rice).
- `TasteProfile` = pure function of the append-only `SwipeEvent` + `MealLog` history, 30-day
  exponential decay, tanh-normalised per-tag affinity. Never persisted, can't go stale.
- `DeckBuilder` composes ~20 cards per deck: ~80% exploit (top score) / ~20% explore (low
  `evidence` tags), deterministic under a seed (SplitMix64) so it's testable.
- Every card carries a plain-language explanation built from the top scoring contributor.
- All weights live in one `ScoringConfig` value type — tunable without code changes.

### 5.6 Seed data (the biggest non-code task)
Authoring rules, enum tables and the frozen id lists: **`docs/design/SEED_GUIDE.md`**.
- Layout under repo-root `seed/`, bundled into the app as-is with no merge step.
  - `manifest.json`: `seedVersion` plus the ordered lists of fragment paths.
  - `ingredients/*.json`: 224 Indian kitchen ingredients (target 220–280) (id, name, aliases, category,
    role, buyFrom, shelfLifeDays), split into 3 fragments, rows sorted by id.
  - `recipes/*.json`: ~80 pan-Indian everyday recipes (breakfasts, dal/sabzi staples, rice
    dishes, quick snacks, plus craving dishes like chole bhature, dosa, pav bhaji, biryani),
    split into 6 fragments, each with closed-enum tags.
- `SeedCodec` and `SeedValidator` live in `KyaCore/Sources/KyaCore/Seed/`. The codec is
  strict: unknown keys and unknown enum values are errors with a file/path location, and
  it forces `source=seed` / `isUserCreated=false`. The validator enforces referential
  integrity (every recipe ingredient id exists), unique ids and aliases, role and
  buyFrom conventions, and coverage targets.
- **Photos:** v1 ships with every `imageAsset` null, and the app renders a gradient+initial
  fallback. When photos arrive, `imageAsset` is `images/<recipe id>.webp`, relative to
  `seed/`. They must be free-licensed (CC0/PD/Unsplash/Pexels preferred), credited in
  `seed/IMAGE_CREDITS.md`, webp, and ≤60 KB (~40 KB target).
- Written by us (Kaggle "Indian Food 101" is inspiration only, pending licence check).
- Loaded into SwiftData on first run. `seedVersion` in `manifest.json` lets later seed
  recipes be added without clobbering user edits.

### 5.7 Example data flow: "I made this"
```
HomeView → MealStore.cook(recipe)              (@Observable, @MainActor)
  → MealLogRepository.add(log)                 (KyaCore port → SwiftData adapter)
  → shows "Used up anything?" sheet (perishables pre-listed)
  → PantryRepository.setLevels(confirmed changes)
  → stores refresh from the repositories → Home + Pantry views update via Observation
```

### 7.1 Porting rules (M1', M2')
- **Expected values are frozen.** Copy them from the Dart tests in `legacy/`. Never
  recompute them from the Swift implementation. If Swift disagrees, Swift is wrong until
  proven otherwise, and a deliberate behaviour change needs a note in this file.
- **Dictionary and Set iteration order is random in Swift** (it is per-process seeded).
  Any output order that depends on iteration needs an explicit tie-break, by `id` unless
  the Dart code breaks ties differently.
- **Seeded RNG = SplitMix64** in `KyaCore/Support`. Dart's `Random(seed)` sequence can't
  be reproduced, so the DeckBuilder tests that depend on the shuffle become property tests
  (composition counts, no duplicates, cooldown exclusion, same seed gives the same deck).
  These are the **only** goldens allowed to change.
- **Strict seed parsing:** use `JSONSerialization` plus explicit key checks (reject
  unknown keys, require the required ones, check types). Plain `Codable` silently ignores
  unknown keys, so it can't be used for seed decoding.
- **Calendar days:** use `Calendar` with an explicit `TimeZone`, plus `startOfDay` and
  `dateComponents([.day], ...)`. Never divide seconds by 86400.

## 8. Risks

| Risk | Mitigation |
|---|---|
| Users stop updating the pantry | Level-based stock, assumed staples, "used up?" sheet, shopping→pantry auto-move |
| Seed data quality/effort | Dedicated M2 milestone, validators, real household recipes |
| Ingredient naming chaos | Canonical ids + aliases; unmatched input becomes a user ingredient, never fails |
| Scoring feels "off" | Config-driven weights, per-card explanations, golden-test regressions |
| Port drifts from Dart behaviour | Frozen goldens from `legacy/`, porting rules in §7.1, explicit tie-breaks, TZ test run |
| Data loss (no cloud in v1) | JSON backup/restore now, sync in v2 |
| Taste profile filter bubble | 20% explore cards, weak left-swipe signal, 30-day decay, "Reset my taste" |
| Swipe fatigue / mis-swipes | Undo, equivalent buttons, 20-card deck cap, left = soft signal |
| Photo licensing / app size | Licence-clean sources, credits file, webp size budget, placeholder fallback |
| Scope creep | This doc's explicit YAGNI list; v1.1 decided only after dogfooding |
| iOS-only misses Android households | Accepted trade-off (ADR 009); revisit after v1 dogfooding |
| A needed package is blocked by the proxy | Zero-dependency policy; any dependency needs an ADR |
| TestFlight needs a paid account | Still needed by M8 |

### 9.1 Why we left Flutter
In short (full evidence in ADR 009): macOS security tooling deletes the Flutter SDK's
`dartaotruntime` and `impellerc`, which breaks `flutter build`, `flutter test`,
`dart test` and `dart analyze` locally. The corporate proxy also returns `403
MediaTypeBlocked` for many pub.dev archives, and there is no internal pub mirror.
**Don't** restore those binaries, strip quarantine, pin versions around the filter,
preload archives or go off VPN. Those are decisions for Yasher and IT. The legacy
oracle can still be checked with `legacy/tool/check.sh`, which runs on the JIT VM.
